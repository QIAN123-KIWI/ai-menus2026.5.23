# AI Menu Translator V2 Product Requirements

## 一句话目标

把用户在餐厅拍到的任意语言菜单图片，快速变成适合中国用户点餐的中文菜单，同时保留原文给店员确认；文字必须先出来，图片永远不能阻塞点餐。

## 核心使用场景

1. 用户在日本、韩国、泰国、越南、英文等餐厅拍一张或多张菜单照片。
2. 系统边识别边显示菜单项，不能等所有图片和所有翻译完成才一次性出现。
3. 用户看到中文菜名、原文、发音辅助、价格、分类，可以加入购物车。
4. 用户给店员看订单页，订单页默认显示菜单原文，标题和提示语使用菜单当地语言。
5. 菜品无图时默认显示“无图/点击生成”，用户点无图位置才生成示意图；生成后缓存，下次同菜复用。

## 必须满足

### 1. 速度

- 首条中文菜品必须尽快出现，目标 `5-8s`，复杂大图允许到 `15s`。
- 识别过程中 `已找到 N` 必须持续变化，不能长时间停在 0。
- 每识别/翻译出一批可用菜品，就要追加或刷新到页面。
- 不能等整张菜单全部 OCR 完、全部翻译完、全部分类完才显示。
- 支持多张照片一起上传，照片之间可以并发处理。
- 高并发优先，当前阶段允许增加模型调用成本换速度和准确率。

### 2. 翻译质量

- 所有非中文菜单都必须显示中文菜名，不能只显示日文、韩文、罗马音或原文。
- 中文要适合点餐，不要生硬直译。
- `Highball`、`大阪烧`、`牛丼`、`生拌牛百叶`、`韩式血肠` 等餐饮专有词必须翻译准确。
- 日文菜单必须保留：中文主标题、日文原文、假名、罗马音。
- 韩文菜单必须保留：中文主标题、韩文原文，必要时补罗马音。
- 价格不能被当成菜名，例如 `1合 500`、`2合 900` 这类如果是酒水规格，要变成正确酒水/规格项，不能单独变成菜品。
- 标题、广告、电话、营业时间、税费说明、店名、分类标题不能进入菜品列表。

### 3. 分类

- 分类必须是中文，让中国用户看得懂。
- 分类来自菜单自身结构或模型判断，不能固定死为“前菜/沙拉/汤品/主食”。
- 禁止出现兜底脏分类：`菜单分类`、`招牌菜` 这类标题如果不是实际分类不能展示。
- 同一道菜不能先出现在“总结果/今日推荐”，后面又在真实分类里出现第二次。
- 分类可以动态出现，但切换分类时不能隐藏用户已经识别到的有效菜。

### 4. 去重

- 同一张照片不同切片识别出的同一道菜必须合并。
- 多张照片重复拍到同一道菜时也要合并。
- OCR 小差异也要尽量合并，例如 `チキンカレー` 和 `チキンカレーライス` 要按语义区分，`丼丼` 这种明显错字要纠正。
- 合并时保留质量更高的版本：有中文、有原文、有假名/罗马音、分类更准确、价格更可信的条目优先。

### 5. 图片生成

- 默认关闭自动生图。
- 文字菜单先秒开，图片不参与识别主流程。
- 没有图的菜显示“无图/点击生成”。
- 用户点击无图位置时才生成单道菜示意图。
- 生成成功后缓存；同一道菜下次直接读缓存。
- 生成失败不能影响菜单识别、点餐、结算。

### 6. 多照片导入

- 上传新照片不能自动清掉已有菜单。
- 只有用户点击清理/重新导入时才清空旧菜单。
- 支持图库多选。
- 支持手机/浏览器直接拍照导入。
- 重复照片或重复菜单页不能造成重复菜品。

### 7. 购物车和店员页

- 用户可以加减菜品数量。
- 购物车总价按当地货币显示。
- 日元、韩元、人民币、泰铢、越南盾等单位要按当地习惯放在数字后面或前面。
- 店员页默认显示原文，方便店员核对。
- 店员页保留中文辅助，但不能覆盖原文。
- 发音按钮按菜单原语言朗读。

### 8. 部署与密钥

- 线上公开使用时必须走服务端代理，API Key 放服务端。
- 前端不能暴露 API Key。
- 腾讯云优先，因为需要后端代理和密钥保护。
- GitHub Pages 只能作为纯静态备用方案，不能单独承担公开线上版本。
- 部署前必须先本地网页端测试通过。

## 当前不达标的问题

- 中文出现仍然偏慢，复杂图片首批中文有时超过 `15s`。
- 当前链路仍偏向“先 OCR 一批，再翻译一批”，还没有真正做到“单项 OCR 后立刻翻译并显示”。
- 大菜单、斜拍、手写黑板菜单存在漏项。
- 部分日文 OCR 错字会导致翻译不准。
- 分类和去重已经改善，但需要继续用网页真实上传流程验证，而不是只看脚本。
- 腾讯云函数部署还未完成最终可用链路。

## 建议的正式技术路线

1. 前端上传图片后，服务端立即创建任务并返回流式响应。
2. 服务端先生成轻量预览图，快速跑视觉 OCR，拿到首批原文。
3. 每拿到一小批原文，立刻并发调用高质量文本模型翻译成中文。
4. 翻译结果一批一批发给前端，前端用“替换式累计结果”刷新列表。
5. 后台继续切片细扫，补全漏项。
6. 最后跑一次全局清洗：去重、过滤标题、修正明显 OCR 错字、统一分类、统一价格货币。
7. 图片生成完全独立，只由用户点击触发。

## 验收清单

- `测试2` 文件夹里的所有图片都要本地网页上传测试。
- 首批中文出现时间：普通图 `<= 8s`，复杂图 `<= 15s`。
- 识别过程中 `已找到 N` 至少变化 2 次。
- 最终列表不能有未翻译中文项。
- 最终列表不能有同菜同价重复项。
- 最终列表不能有标题、电话、营业时间、税费说明。
- 日文条目要有原文、假名、罗马音。
- 韩文条目要有原文和中文。
- 多张图片连续上传时，旧菜单不自动消失。
- 点击清理后菜单清空，可以重新导入。
- 默认不自动生成图片。
- 点击无图能生成并缓存图片。
- 店员页显示原文并能朗读。
- 本地网页测试通过后，再部署腾讯云。
- 腾讯云线上 `/api/health` 和完整图片识别流程都必须通过。
